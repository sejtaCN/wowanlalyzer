# 攻略内容生产规则

> 本文档是攻略正文（章节稿）的唯一规范源。写新专精的章节、改已有章节的文案、
> 评审别人交上来的章节稿，都以这份为准。
>
> 机器可读的同一套设定在 `content/guides/copy-rules.json`，门禁按它执行：
> `npm run check:copy`（文案）、`npm run check:doc`（文档与落盘逐字一致）。

## §1 参照模板与总则

### 1.1 模仿模板

参照模板是 NGA《[攻略套娃]职业攻略撰写心得》（tid=32191378，2022-06-05，分逻辑篇 /
排版篇 / 措辞篇 / 其他与后记四篇），对标的成品是 NGA 魔兽世界板块的精华攻略帖。
本地镜像 `content/guides/sources/nga-maxroll-12.0.md`。

模仿的是**骨架与句式**，不是理由句。引用别人的结论时只引数据，理由必须自己给证据。

模板里可直接执行的判据有五条：

| 判据 | 原文主张 | 本项目的落地 |
|---|---|---|
| 提高实质性语句占比 | 「减少废话，书面化一点，就是减少非实质性语句」 | 删设问、删分析过程、删评价性副词 |
| 书面化用词 | 点名回避「我们」「接下来」「我觉得」 | 见 §4.1 句式规范 |
| 重点加粗或变色 | 「出现一大段连续文字时，一定要用加粗或变色突出重点语句」 | 结论句独立成段，关键词加粗 |
| 并列用列表 | 「在列出多条并列内容的时候，用列表功能列出来」 | 见 §3.1 图表条件列 |
| 次要细节折叠 | 「不是很重要、或多数玩家不关心的数值计算部分用 collapse 折叠」 | 见 §3.3 优先级依据 |

### 1.2 七条铁律

1. **写「怎么做」，不写「怎么做的」**——不描述实现过程。读者不关心代码怎么搭。
2. **结论前置**——先给该做什么，再给为什么，最后给数据。
3. **一句话只做一件事**——禁三段式并列（结论＋补充＋免责）。
4. **数字不许裸奔**——每个数字带单位、带口径，且能追到来源。
5. **读者不关心内部产物**——机器语法、文件路径、批次号、门禁术语不进正文。
6. **边界用读者语言写**——写清缺什么、怎么补，不写免责套话。
7. **保留全部原有信息**——改写只改表达。数值、来源、时间戳、章节结构、字段角色一概不动，
   不新增任何未经证实的内容。

## §2 写作流程

七步，按序走。每一步都有产出与自检，跳步必然后面返工。

### 第 1 步 · 定这一页回答的问题

先写标题、副标题，标题必须是**读者会问的问题**，不是栏目名。

- ✅ `中波（5–9 只）` / `大波（≥10 只）`
- ❌ `波次模型页` / `爆发分析`

副标题补一句「这一页值不值得看」，不超过 25 字。

**自检**：把标题念给没读过这一页的人听，他能不能判断要不要看。

### 第 2 步 · 取数并锁定出处

每个数字进场前先确认出处：模拟记录（runId）或真实日志事件。追不到出处的数字**删掉**，
不是降级表述。

每个 runId 必须带模拟器版本、commit、迭代数、95% 置信区间、生成时间。
日志类结论必须能追到具体事件（时间戳＋技能＋目标）。

**自检**：把正文里每个数字列出来，逐个指出它的出处。指不出的就删。

### 第 3 步 · 先写结论句

按 §3 的骨架，**先填结论那一句**，再回头补数值和阈值。顺序反了必然写成数据堆砌。

结论句的写法（详见 §4.1）：动词开头，一句话给动作，数字跟在后面。

**自检**：只看结论句，读者能不能开始操作。

### 第 4 步 · 按四类规范填字段

章节里的每一段文字都属于四类之一（§3）：图表与数据描述 / 技能介绍 / 技能优先级 /
可视化部分。逐段对号入座，按该类的骨架、必填要素、用词规范写。

**自检**：每一段都能归到 §3 的某一类，没有归不上的段落。

### 第 5 步 · 术语本地化

按 §4.2 的 L1/L2/L3 三分类处理每一个英文词：保留、中文化、或移出正文。
**绝不自造官方译名**——没有出处的中文译名比英文标识符更糟，因为读者会以为它是官方的。

**自检**：正文里没有未框注的英文标识符，也没有来路不明的自造译名。

### 第 6 步 · 通读去 AI 味

按 §5 的十二条逐条扫一遍。这一步不是「润色」，是**结构检查**：AI 味的主要来源是
结构同构（每段都是同一个三段式），不是个别用词。

**自检**：通读一遍，改掉任何能靠「读起来都一样」形容的句子。

### 第 7 步 · 过门禁并同步文档

| 命令 | 查什么 |
|---|---|
| `npm run check:copy` | 禁用词、术语、AI 腔、长度预算、依据与机器原文的对应 |
| `npm run check:doc` | 交付文档与落盘 JSON 逐字一致 |
| `npm run validate:content` | 数字必须有来源、runId 必须存在、图契约齐全 |

**改完 JSON 必须同步交付文档**——`docs/nga-copy-spec.md` §4 是本次的正文快照，
两者一旦漂移，文档就在骗人。`check:doc` 就是为拦住这件事。

## §3 四类内容的表达规范

每类内容的规范由五部分组成：结构骨架 → 必填要素 → 用词规范 → 反例/正例 → 字段落点。
新写一段内容时按这个顺序走一遍。

### 3.1 图表与数据描述

#### 结构骨架

**动作结论 → 数值 → 阈值 → 怎么读**

一句话给动作（做什么），跟着给数值（值多少），再给阈值（什么时候变），
最后一句说清这张图该看哪里。

#### 必填要素

| 要素 | 写什么 | 判定标准 |
|---|---|---|
| 图题 | 读者看完要知道什么 | 不写「这是什么图」 |
| 动作结论 | 动词开头，一句话 | 不含设问句、不含评价性副词 |
| 关键数值 | 原始精度 + 单位 | 不做二次四舍五入 |
| 对比结论 | 和什么比、高了多少 | 必须能回答「相对谁」；不写「提升明显」 |
| 阈值 | 贴紧阈值的写法 | `目标 ≥5 只`、`间隔 <122.4 秒` |
| 误差说明 | 有置信区间就必须交代 | 明写「误差带 ±x%，别把它当收益」 |
| 导读句 | 指出看哪根柱／哪一列／哪一行 | 不复述图上已有的数字 |

**对比结论的三种口径**（都要落到具体基线，不能只给一个百分数）：

| 对比 | 写法 | 例 |
|---|---|---|
| 和不开爆发比 | 明写「开与不开差 x%」 | `开与不开差 44.0%，一次爆发多换 12.7M。` |
| 和另一档比 | 明写比的是哪一档 | `一次只换 4.93M，不到大波的 39%` |
| 和自己的误差带比 | 明写这差额在不在误差内 | `AoE 开不开的差落在 CI 内` |

#### 用词规范

- 结论句动词开头：`4 只以下不开爆发。` 不是 `关于爆发，这里需要注意的是……`
- 数值与单位紧连：`12.7M`、`43.98%`、`155.6 秒`、`30 秒`
- 阈值用符号贴紧：`≥ 5 只`、`≤ 2 只`、`> 2`
- 区间用短横：`5–9 只`、`9.3–11.6M`
- 百分比必须能回答「相对谁」——口径写进图例或导读
- 误差带写成误差，不写成收益

#### 反例 / 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| `他这一场的整场读数` | 图题在描述图，不在告诉读者看什么 | `整场读数：持续伤害覆盖了几个目标、爆发开了几次` |
| `开与不开的差：+44.0%，一次爆发多 12.7M；误差带 ±0.26%。` | 三段式并列，读者要自己拆 | `开与不开差 44.0%，一次爆发多换 12.7M。误差带 ±0.26%，别把它当收益。` |
| `这一波要加 2 条、要降 2 条；序号来自 APL 表，理由各自挂证据。` | 三段式并列，一句里塞了三件事 | `这一波加 2 条、降 2 条。序号是 APL 表里的真实位置，每条都挂着理由。` |
| `目标档与 BOSS 档分别读取对应 runId；超过 8 只按 8 只档。` | 内部产物外泄 | `这一波 13 只，模拟按 8 只档算，读作保守下限。够用来决定「开 / 看冷却 / 不开」。` |

#### 字段落点

`claim`、`chart.title`、②段导读、`casePanel.points[]`、顶图带「一条数字结论」格。

**claim 里的数字一律写占位符**，例如 `单体 {{bossDurationSec}} 秒只换 {{bossDamageM}}M`，具体数值在同章 `claimFields` 里挂 runId（`pair` 取配对差值 / `runId` 取时长目标数 / `of` 取比值）。渲染由 `apps/web/src/data/claim.ts` 负责；写死数字会被 `validate:content` 直接拦下（门禁自检里有一条坏样本专门试这个）。

### 3.2 技能介绍

#### 结构骨架

**定位 → 机制要点 → 适用场景 → 收益**

四件事各一句，说清就停，不重复堆叠。同一技能的四种说法不互相复述。

| 要素 | 回答的问题 | 写法 |
|---|---|---|
| 定位 | 这个技能干什么 | 一句话，动词开头，不带条件 |
| 机制要点 | 什么条件触发、什么时候不触发 | 条件翻译成人话，否定用否定说法 |
| 适用场景 | 什么时候该用它 | 给场景（这一波 / 开打前 / 冷却好了），不给概率 |
| 收益 | 值多少 | 有实测就写数；没有就写清「值多少靠什么判断」 |

#### 必填要素

- **中文技能名**——正文只出现中文，英文键放进悬停提示，不占正文行。
- **四件事齐**——缺哪一件就在内容层补数据，不要在正文里含糊过去。
- **条件人话化**——机器条件逐条翻译，否定用否定说法。
- **分支阈值**——条件分支必须给触发阈值（目标数、剩余血量%、冷却秒数）。

#### 用词规范

- 技能名以 `skills.json` 为准；没有官方中文名的天赋／增益／变量，用 `「」` 框成标识符，
  **不自造译名**。
- 动词用实词：给／铺／挂／留／吃满／摊薄／轮不上。不用「使用」「保持」「考虑」「进行」。
- 条件写成 `X 时 Y` 或 `如果 X，就 Y`。
- 不用「注意」「尽量」「合理」「视情况」——这些词后面必须跟一个具体动作。

#### 反例 / 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| 技能卡下面挂一行 12px 灰字 `tentacle_slam` | 内部标识符占了正文位 | 只显示「触须猛击」，鼠标悬停才显示英文键 |
| `APL: active_dot.shadow_word_pain>=active_dot.vampiric_touch` | 裸机器语法 | `已挂暗言术：痛的目标数 ≥ 已挂吸血鬼之触的目标数` |
| `这个技能在合适的时候用会很有用` | 形容词代替信息 | `持续伤害没铺满时，不要拿它换刷新` |

#### 字段落点

`skills.json` 的 `zh`、L0-02 技能清单、优先级卡的条件行、技能卡的 `title` 悬停。

### 3.3 技能优先级

#### 结构骨架

**分级 → 理由 → 依据 → 条件分支**

#### 分级方式：只有加／降两档，不用 S/A/B

本项目的优先级**不设 S/A/B 档**。原因有三：

1. S/A/B 是**主观评级**，读者问「为什么它是 A 不是 B」时无法用数据回答。
2. 本项目的结论已经锚在真实执行位置上——「加／降」说的是**相对基础循环改了什么**，
   读者能直接对照自己的按键顺序。
3. 档位越多，档与档之间的边界越需要额外解释；两档不需要解释。

| 分级 | 含义 | 序号 |
|---|---|---|
| 加 | 相对基础循环，这一波往上提 | 用优先级表里的真实执行位置（`#1` / `#2` / `#3`） |
| 降 | 相对基础循环，这一波往后挪 | 同上 |

序号不是排名，是**位置**。同一个位置被多条命中时只画一个点。

#### 必填要素

| 要素 | 写什么 | 判定标准 |
|---|---|---|
| 分级 | 加 / 降 | 只有两档 |
| 序号 | 优先级表里的真实位置 | 与表一致，不是自编排名 |
| 理由 | 一句话 | 句式是「条件 → 结论」，不反问 |
| 依据 | 人话依据 | 是原条件的中文翻译，不加解释、不加结论 |
| 机器原文 | 可折叠 | 与人话依据并列存在，信息一条不丢 |
| 条件分支 | 触发阈值 + 后果 | 写清阈值（目标数／剩余血量%／冷却秒数） |

#### 条件分支：三种来源，三种写法

条件分支必须同时写清**触发阈值**和**后果**，两样缺一不可。触发源分三类，措辞跟着变：

| 触发的是什么 | 怎么表述 | 例 |
|---|---|---|
| 天赋变化 | 点没点某个天赋，点名的天赋用「」框住 | `并且点过「devour_matter」天赋` |
| 装备或外部增益变化 | 有／没有这个增益 | `有「共振能量」增益时`；外部增益单独触发写作 `外部增益` |
| 波次条件变化 | 目标数／剩余血量／冷却秒数 | `目标 ≤2 时 AoE 循环不启动` |

三种来源都不许只写「条件满足时」。条件满足是废话，阈值才是内容。


#### 用词规范

- 理由句式：`只有残血目标才进循环，中波轮不上它`、`目标 ≤2 时 AoE 循环不启动，填充技能重新有用武之地`。
- 不写「为什么不能反着来」这类反问，只写结论。
- 阈值贴紧写：`≥5 只`、`<122.4 秒`、`≤20%`。
- 三个标签各指其物，不混用：

  | 标签 | 指什么 | 出现在哪 |
  |---|---|---|
  | `APL 条件：` | 机器条件的中文翻译 | 依据行的开头 |
  | `APL 原始写法` | 机器语法原文 | 依据行下方的折叠条标题 |
  | `APL 原文` | 泛指机器语法 | 仅用于文档叙述，不作界面标签 |

- 同一组里两条依据**不允许共用同一句话**——写串了就是错，依据必须各自对得上自己的原文。

#### 反例 / 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| `APL: actions.main 顺序里 vampiric_touch 排在填充技能之前` | 裸机器语法 + 英文键 | `APL 条件：「actions.main」里，吸血鬼之触排在填充技能之前`（原文进折叠区） |
| `优先级表：「actions.cds」的末位` | 只说位置不说后果 | `它保命用，别混进爆发序列` |
| `S 档：影王斩` | 主观评级，无法用数据回答 | `加｜虚空齐射：多目标时它覆盖的目标最多，冷却好了就用` |

#### 字段落点

`priorityDiff.reason`、`priorityDiff.evidence`、`priorityDiff.raw`、优先级表的条件列。

### 3.4 可视化部分

#### 结构骨架

**这张图看什么 → 怎么读 → 边界在哪**

#### 必填要素

| 要素 | 写什么 | 判定标准 |
|---|---|---|
| 看什么 | 图回答哪个问题 | 段导读首句 |
| 怎么读 | 柱高／位置／颜色／数量各代表什么 | 读者看完知道该看哪里 |
| 界面指引 | 点哪里会看到什么 | 说清交互后果，不说「点击查看」 |
| 流程／路线顺序 | 顺序编号 + 箭头连接 | 不写成一段散文 |
| 边界 | 缺什么、为什么没有 | 没有坐标不标坐标，没有分段不假装有分段 |

#### 用词规范

- 流程与路线用 `① 认规则 → ② 分波次 → ③ 进路线` 这种编号＋箭头。
- 界面指引写结果：`点任意一波，上面的结论、下面的数值、地图注记会一起换`。
- 边界句给读者语言：`路线没有每波坐标，这张图只给地形，不标位置`。
- 不自述页面实现：`本页不引用模拟`、`这里只回答……` 这类自述删掉。

#### 反例 / 正例

| 反例 | 问题 | 正例 |
|---|---|---|
| `平面图只回答“整张地牢长什么样”；波次顺序看上面的路线条。` | 元层自述 | `借这条真实路线说明模型。路线没有每波坐标，不往图上标位置。` |
| `选波看第①段；这一段只核对地形，不给不存在的波次坐标。` | 否定式绕口 | `选波看第①段。这一段只核对地形：路线没有每波坐标，不给不存在的点位。` |
| `整场日志推断出的阶段，不是单波：这份导出没有死亡事件，切不出「第 N 波几时开始」。` | 前半句自述 + 三段式 | `整场日志推出的阶段，不是单波。这份导出没有死亡事件，切不出「第 N 波几时开始」。` |

#### 字段落点

①段导读、④段导读、`chart.kind`、`map`、路线图注记。

## §4 通用语言规范

### 4.1 句式：五类句

| 句型 | 结构 | 规矩 |
|---|---|---|
| 结论句 | 动词开头，句号收尾 | 不出现主语「我们」；不反问 |
| 数值句 | 数字＋单位紧连 | 数值前后不加解释性从句 |
| 并列句 | 用「、」或「；」分隔 | 不用逗号连成长串；并列项超过三条改列表 |
| 条件句 | 「如果 X，就 Y」或「X 时 Y」 | 阈值写成 `≥ 5 只` 这种紧贴形式 |
| 收尾句 | 一句话给限制或边界 | 不写免责套话 |

**人称**：第二人称「你」只用于操作指令；「我们」不用于结论。
**动词**：用实词，不用「进行」「实现」「达成」「保持」。
**自指**：不写「不用改界面」「页面自动长出来」「这是真实组件的骨架」。

### 4.2 术语三分类

| 级别 | 定义 | 处理方式 | 本项目实例 |
|---|---|---|---|
| **L1 · 保留英文** | 中文玩家圈通用缩写，离开中文语境也无歧义 | 正文直接用，首现处挂悬停 | DPS、APL、GCD、CI、DoT |
| **L2 · 中文化** | 有确定中文译名且读者能理解 | 页面写中文，英文进悬停 | 模拟器（SimC）、重合度（Jaccard）、技能优先级表（APL） |
| **L3 · 移出正文** | 内部实现产物，读者零收益 | 移出页面（折叠区／数据面板） | APL 表达式原文、英文技能键、场景 id、文件路径、批次号 |

**绝不自造官方译名**。没有出处的中文译名比英文标识符更危险——读者会默认它是官方的。

### 4.3 数字与单位

- **单位不省略**：`12.7M` 保留社区写法，但补全成 `12.7M 伤害`。
- **精度不二次处理**：原始精度直接用，不四舍五入到整数。
- **百分比带口径**：`+44.0%` 必须能回答「相对谁」。
- **时间**：`30 秒`（正文）；图内刻度可写 `30s`。
- **阈值贴紧**：`目标 ≥5 只`、`间隔 <122.4 秒`。

### 4.4 标点与排版

- 句号收尾；不用省略号、不用感叹号。
- 并列用「、」或「；」。
- 数值与单位紧连；区间用短横 `5–9 只`。
- 关键词加粗或变色，其余留白。
- 中文排版按 W3C clreq：汉字与西文之间留 1/4 汉字宽；行首行尾禁则；
  禁 `word-break: break-all`；西文单词不跨行断开。

### 4.5 长度预算

| 字段 | 上限 |
|---|---|
| `subtitle` | 25 字 |
| `claim` | 120 字 |
| `priorityDiff.reason` | 60 字 |
| `priorityDiff.evidence` | 80 字 |
| 段导读 | 90 字 |
| `casePanel.points[]` | 70 字 |

超预算不是硬错，但必须说明为什么超——通常是这一句在同时做两件事，拆开。

## §5 AI 味：十二条常见形态与改动方案

AI 味的主要来源不是个别词，而是**结构同构**：每段话都是同一个骨架（结论＋补充＋免责），
读三段就腻。以下十二条按出现频率排序，每条给出症状与改动方案。

### 5.1 三段式并列

**症状**：每段说明都是「结论＋补充＋免责」三段，以分号并列收尾。12 处以上。

> 改前：开与不开的差：+44.0%，一次爆发多 12.7M；误差带 ±0.26%。

**改动**：拆成两句，第一句只给动作与数值，第二句只交代边界。超过两句的部分折叠或删掉。

> 改后：开与不开差 44.0%，一次爆发多换 12.7M。误差带 ±0.26%，别把它当收益。

### 5.2 设问句与分析过程

**症状**：`我们该如何选择 X 的用法呢？其实这是很简单的，首先……`

**改动**：删掉设问与分析过程，直接给结论。原帖的判据是「增加实质性语句的占比」。

> 改后：龙神附体在循环中十分重要，由于它的 CD 比 120 团辅少 10 秒，在不会损失使用次数的情况下，可以把龙神附体延后 10 秒到团辅期中，让龙神附体后的爆发技能吃到团辅加成。

### 5.3 评价性副词

**症状**：`如此重要`、`无疑`、`其实很简单`、`十分关键`。

**改动**：删掉。重要性由数字承担，不由形容词承担。

### 5.4 口语化自指

**症状**：`我们`、`接下来`、`我觉得`、`下一个是`。

**改动**：删掉。原帖点名这些词在文字攻略里应当尽量少出现——「我觉得」更不该出现在能靠计算得出的结论里。

### 5.5 自指与自夸

**症状**：`不用改界面`、`页面自动长出来`、`这是真实组件的骨架`、`接上新专精只需要数据`。

**改动**：删掉整句。读者不关心代码怎么搭；这类话暴露的是作者在向同行汇报，不是在对读者说话。

### 5.6 开发中间文字

**症状**：`按 B3 顺序补`、`还没写`、`content/sims 下的一个同名文件`、`状态改成 active`。

**改动**：换成读者语言，或让这类页面本来就属于元层（那页是给开发者看的，可以保留）。

| 改前 | 改后 |
|---|---|
| 还没写 | 这一层还没有章节 |
| 按 B3 顺序补：暗牧在做什么 → 技能清单 | 计划顺序：认技能 → 技能清单 |
| 每一行都对应 content/sims 下的一个同名文件 | 点开任意一行，看它的模拟版本、迭代次数和误差范围。 |
| 状态改成 active | 状态变成「已上线」 |

### 5.7 内部标识符裸奔

**症状**：APL 表达式、英文技能键、场景 id、文件路径、批次号、脚本名出现在正文。

**改动**：L1/L2/L3 三分类处理（§4.2）。机器语法下沉到折叠区，英文键进悬停，
场景 id 改中文描述（`w30_8` → `8 只目标 · 30 秒`）。

### 5.8 免责套话

**症状**：`仅供参考`、`可能存在误差`、`具体情况具体分析`、`后续会优化`。

**改动**：换成具体的边界陈述——缺的是什么、补上它需要什么。

> 改前：限制：只有施法/增益/减益，没有死亡事件；怪物名后续编号会被复用；全程无空场。所以这是阶段级推断，不是单波。

> 改后：这段只能看到「哪个阶段他开了爆发」，看不到「第几波」。要读到单波，需要一份带战斗分段的日志。

### 5.9 并列长句

**症状**：条件列整段挤成一个单元格，逗号连成长串。

**改动**：并列改列表；机器条件的顶层「或」拆成可扫读的短语行，用金色「或」分隔。

### 5.10 数字埋在长句里

**症状**：精度合格，但结论和数字之间隔着太多字，读者扫不到。

**改动**：结论前置，数字紧跟结论句，保留原始精度。

> 改前：他这一场：吸血鬼之触平均挂在 4.91 个目标、暗言术：痛 4.68 个，虚空形态开了 11 次、每次约 35.5 秒。

> 改后：他这场：吸血鬼之触平均挂 4.91 个目标，暗言术：痛 4.68 个；虚空形态开了 11 次，每次约 35.5 秒。

### 5.11 字面 Markdown 记号

**症状**：`**重合度**` 写进了渲染成普通文本的容器里，星号原样显示在页面上。

**改动**：用真标签（加粗标签）而不是 Markdown 记号；同时在门禁里加一条
「页面可见文本不含 `**`」的断言。

### 5.12 形容词代替数据

**症状**：`伤害提升比较明显`、`收益相当可观`。

**改动**：写死数字。原帖不写「提升比较明显」，写「提升约 12.7%」。

### 5.13 这一节的自查

改完逐条问一遍：

1. 每段都是同一个三段式骨架吗？是 → 拆。
2. 有设问句吗？有 → 删。
3. 有评价性副词吗？有 → 删。
4. 有「我们」「接下来」「我觉得」吗？有 → 删。
5. 有自指或自夸吗？有 → 删。
6. 有内部标识符裸奔吗？有 → 本地化或下沉。
7. 有免责套话吗？有 → 换成具体边界。
8. 有数字被埋在长句里吗？是 → 结论前置。
9. 有形容词代替数字吗？有 → 写死数字。
10. 段落之间读起来「都一样」吗？是 → 重写。

## §6 章节骨架

### 6.1 五段固定结构

每章固定五段，顺序不变（**图契约**与页面模板一一对应）。段标题必须是**读者会问的问题**，
不是栏目名：

| 段 | 段名（内部用） | ✅ 标题写法（读者看到的） | 数据来源 |
|---|---|---|---|
| ① | 模型卡 | 这一波几只、活多久 | 路线（波次）+ 假设（时长） |
| ② | 主图 | 开爆发值多少 | 模拟记录 |
| ③ | 技能调整 | 这一波技能顺序怎么改 | 优先级表 + 模拟 |
| ④ | 地图 | 落到真实路线是什么样 | 路线瓦片 |
| ⑤ | 高手对照 | 真人怎么打 | 真实日志 |

### 6.2 段 × 内容类型 × 字段对照

这张表是写章节时的对照标准——照着填。

| 段 | 内容类型 | 规范节 | 主要字段 |
|---|---|---|---|
| ① 模型卡 | 图表与数据描述 | §3.1 | `model`、①段导读 |
| ② 主图 | 图表与数据描述 | §3.1 | `chart.title`、`claim`、②段导读 |
| ③ 技能调整 | 技能优先级 | §3.3 | `priorityDiff.reason/evidence/raw` |
| ④ 地图 | 可视化部分 | §3.4 | `map`、④段导读 |
| ⑤ 高手对照 | 图表与数据描述 | §3.1 | `casePanel.headline/points/evidence/reading` |
| 技能清单页 | 技能介绍 | §3.2 | `skills.json`、技能卡 |

### 6.3 三条内容红线

1. **没有出处的数字不许出现在页面上。** 构建期扫描，查不到来源直接失败。
2. **切不出边界的结论不硬套。** 日志切不出「这一波」就写「切不出来」，
   不拿整场统计冒充单波。
3. **引用别人的数据必须标出处，且不复制它的理由**——理由要有自己的证据。

## §7 自检清单

写完一章，逐条过。

**结构**
- [ ] 首屏能读到一句可执行的结论？
- [ ] 每段都能归到 §3 的某一类内容？
- [ ] 段标题是读者会问的问题，不是栏目名？
- [ ] 每段有图或表？图契约状态登记了？

**数据**
- [ ] 每个数字都能追到模拟记录或日志事件？
- [ ] 百分比能回答「相对谁」？
- [ ] 误差带写明是误差，不是收益？
- [ ] 阈值贴紧写，且和结论挨在一起？

**语言**
- [ ] 通读一遍，没有「都一样」的段落？
- [ ] 没有设问句、评价性副词、自指自夸、免责套话？
- [ ] 英文全部按 L1/L2/L3 处理过？
- [ ] 没有自造的官方译名？
- [ ] 长度都在预算内？

**依据**
- [ ] 每条优先级依据都能对上自己的机器原文？
- [ ] 同一组里没有两条依据共用同一句话？
- [ ] 人话依据和机器原文都在，一条没丢？

**交付**
- [ ] `npm run check:copy` 通过？
- [ ] `npm run check:doc` 通过（文档已与 JSON 同步）？
- [ ] `npm run validate:content` 通过？

## §8 文档分工与引用关系

| 文档 | 定位 | 与本文档的关系 |
|---|---|---|
| **本文档** `guide-content-rules.md` | **文案与内容结构的唯一规范源** | — |

| `ui-blueprint.md` | UI 设计源（token、逐页设计） | 视觉与版式依据；文案语气一节与本文档 §1.2 对齐 |
| `writing-style.md` | 页面级写作规范（六条） | 本文档 §4 的精简版；界面层细则以它为准 |
| `product.md` | 产品定义 | 章节结构的红线（§6.3）出自 §6 |
| `curriculum.md` | 教学内容规划 | 章节顺序与每章五段的出处 |
| `workflow.md` | 从数据到页面的流程 | 本文档 §2 的工程侧对应 |
| `figure-contract.md` | 图契约与门禁 | §6.1 五段结构的图侧定义 |

**引用方向**：写正文查本文档 → 排版查 `ui-blueprint.md` → 数据查 `workflow.md` /
`methods.md` → 章节结构查 `curriculum.md` 与 `product.md`。

分别以 `ui-blueprint.md` 和 `methods.md` 为准。

**机器可读对应**：`content/guides/copy-rules.json` 存同一套设定，
`npm run check:copy` 按它执行。两边不同步时以本文档为准，并同步修 JSON。
