## §1 适配总则

外部规则书最有价值的不是结论，是**它拒绝什么**。适配时按下面的顺序判断：

| 优先级 | 判断依据 | 处理 |
| --- | --- | --- |
| 1 | 本项目已有设计源（`ui-blueprint.md`）已定义 | 映射到既有 token，不另起一套 |
| 2 | 违反无障碍 / 可读性硬底线（对比度、焦点、动效降级） | 直接采纳 |
| 3 | 与中文排版规范冲突（W3C clreq） | **改写外部规则**，按中文规则走 |
| 4 | 外部规则假定拉丁字母 / 营销页语境 | 降级为提醒，不做门禁 |
| 5 | 纯审美偏好 | 不采纳 |

两条底线：

- **已有系统永远优先。** 外部规则只做两件事：把原则映射到本项目 token 命名上，或在缺失处给建议。不覆盖、不迁移、不引入新构建依赖。
- **不编造规则。** 每条断言都能指回外部规则书的某条，或指回 W3C / WCAG 的某条。

### 1.1 被明确排除的外部规则

| 外部规则 | 为什么排除 |
| --- | --- |
| Refactoring UI 的 16px 基准间距阶（4/8/12/16/24/32/48…） | 直接可用，但下半段对本项目太粗。本项目段内元素极密（表格单元、图例、chip），补 2/4/8 三档，见 §2 |
| Hallmark gate 54「eyebrow 小标签」 | 本项目首页的 `kicker`（"从认技能到进副本"）不是装饰性 eyebrow，是**回答"这一章讲什么"的信息**，删掉会丢失信息。保留 |
| Hallmark gate 63「中点分隔的 meta 串」 | 本项目的 `·` 分隔是**表格里的度量单位列**（"整场实际施法 42 次 · 3.1 次/分 · GCD 中位 1.4 s"），不是模板化的副标题串。保留 |
| Hallmark gate 20「CSS 首行盖章」 | Hallmark 自家的构建标记约定，与本项目无关 |
| Hallmark 48 套主题库 | 本项目是单一暗色主题，不做主题化 |
| Hallmark 的照片素材库（Wikimedia Commons） | 本项目是数据工具，无照片内容 |

## §2 间距

### 2.1 阶的定义

**规则**：所有 `padding` / `margin` / `gap` 的值必须取自下表。

| Token | 值 | 用途 |
| --- | --- | --- |
| `--sp-1` | 2px | 图标↔文字、chip 内边距 |
| `--sp-2` | 4px | 标签↔值、紧贴的元素 |
| `--sp-3` | 8px | 组件内部、标题↔副标题 |
| `--sp-4` | 12px | 卡片内、相关元素之间 |
| `--sp-5` | 16px | 卡片之间、段标题与图之间 |
| `--sp-6` | 24px | 区块之间 |
| `--sp-7` | 32px | 页面大区块之间 |
| `--sp-8` | 48px | 顶图带下、证据条上 |
| `--sp-9` | 64px | 页面级留白 |

外加一个**语义值**：

| Token | 值 | 用途 |
| --- | --- | --- |
| `--gap` | 14px | 段内图间距（设计源 §3.4 已定，被 `check-ui.mjs` 断言） |

### 2.2 为什么是这 9 档，而不是 4px 倍数

Refactoring UI §3.2.2 明确否掉了"4px 倍数"这类线性阶：

> **Rule.** "Everything is a multiple of 4px" is not a system. The scale must account for the **relative** difference between adjacent values.
> **Values.** **No two adjacent values closer than about 25%.**

本项目的阶满足这条：相邻档差 **25%–100%**（2→4 +100%，4→8 +100%，8→12 +50%，12→16 +33%，16→24 +50%，24→32 +33%，32→48 +50%，48→64 +33%）。下半段压到 2/4/8 是本项目的适配——段内元素太密，4/8/12 会让紧凑场景无处落脚。

`--gap: 14px` **不在阶里**，因为它是"段内图间距"这个特定语义的值，塞进阶里会破坏 25% 检验（12→14 只有 17%）。它是单点例外，不参与相邻比。

### 2.3 门禁怎么判

`scripts/check-design.mjs` 做两件事：

1. **阶自身合规**：相邻档差不得低于 25%。改阶时自动校验。
2. **取值合规**：`padding` / `margin` / `gap` / `row-gap` / `column-gap` 的裸 px 值必须落在阶内（`14` 放行）。含 `var()` 的声明不检查。

### 2.4 落地前后

| | 落地前 | 落地后 |
| --- | --- | --- |
| `ui.css` 里的裸间距值 | 23 种 | **9 种**（全部在阶内；`--sp-8` 48px 暂无使用） |
| 落在阶上的比例 | 31% | **100%**（318/318 处） |
| 段间距 / 段内间距 | 22px / 14px | 24px（`--sp-6`）/ 14px（`--gap`） |
| CSS 里的颜色字面量 | 37 种 / 61 处 | **0** |
| 中文标签的正字距 | 13 处 | **0**（3 处负字距保留：`h1`/`h2`/`.brand`） |
| `text-transform: uppercase` | 9 处 | **0** |

## §3 颜色

### 3.1 规则

**颜色只能来自 token。** `apps/web/src/ui.css` 的 `:root` 块是唯一定义处；其余位置一律 `var(--token)`。

SVG 例外：SVG 的 `fill` / `stroke` 支持 CSS 变量，所以依赖图、曲线图、怪物族色板也走 token，TSX 里写 `var(--dep-dot)` 即可，不需要内联色值。

### 3.2 token 分组

| 组 | token | 说明 |
| --- | --- | --- |
| 表面 | `--bg` `--card` `--card-2` `--card-3` `--line` `--line-2` | 底色与描边 |
| 文字 | `--ink` `--sub` `--muted` | 三档，不多不少 |
| 强调 | `--gold` `--accent` `--accent-soft` | 金色 |
| 语义 | `--up` `--down` `--warn` | 绿=增益/开爆发，红=掉 DPS（本站是游戏攻略，不适用中文股市「涨红跌绿」） |
| 图表数据 | `--data-on` `--data-off` `--data-boss` `--data-alt` `--data-flat` `--data-waste` `--data-unused` | **按语义命名，不按色相命名**——换配色时改一处，图例语义不动 |
| 图表轨道 | `--track` `--track-2` `--track-soft` | 柱底、轨道 |
| 图表文字 | `--ink-on-gold` `--ink-on-gold-soft` | 色底上的文字 |
| 依赖图 | `--dep-dot` `--dep-buff` `--dep-burst` `--dep-opener` `--dep-node-*` `--dep-label` `--dep-muted` | `Analysis.tsx` 的 SVG |
| 曲线图 | `--curve-a` `--curve-b` `--curve-up-soft` `--curve-down-soft` `--curve-axis` `--curve-fill` `--curve-label` | `StatCurves.tsx` |
| 骨架屏 | `--skel-base` `--skel-sheen` | `Skeleton.tsx` |
| 怪物族 | `--family-1` … `--family-6` | `WaveDiagram.tsx`，按族名哈希取色，保证同族同色 |

### 3.3 为什么数据色按语义命名

Hallmark gate 74 会报「框架默认色板是 AI 味」，Refactoring UI 法 3 要求「每个值都来自系统」。但更根本的问题是**命名**：色值叫 `#2f9e6a` 时，没人知道它代表什么；叫 `--data-on` 时，换成蓝绿色也不影响任何图例与代码。

规则：**token 名描述它在图里代表什么，不描述它长什么样。**

### 3.4 对比度

WCAG 2.x 相对亮度公式，阈值 4.5:1（正文）/ 3:1（大字）。门禁检查 21 组前景/背景配对，全部取自 token 的实际组合。

当前全部通过，最低一对 `--muted on --card-3` = **6.06:1**。

> 校验算法直接取自 Refactoring UI 的 `check_contrast.py`（WCAG 标准公式，非书的近似式）。

## §4 中文排版

**这是本项目独有的一节。** 两个外部规则书都基于拉丁字母，没有 CJK 处理；Hallmark 甚至把「带字距的全大写标签」列为 Floor 级禁止项——那条规则对中文是**误判**，但指向的视觉问题在中文里同样存在，只是成因不同。

### 4.1 正 letter-spacing 禁用于中文标签

**规则**：打汉字的标签（`--fs-4` 及以下的小标签、表头、导航项、chip）不得用正的 `letter-spacing`。

**为什么**：

- 汉字是等宽方块字，字与字之间本来就没有字形侧的留白。拉丁字母靠字形本身的收笔/伸笔形成视觉间距，加字距是为**字形**服务；汉字加字距是在**字与字之间插空隙**，会破坏中文行的整齐感。
- 这与 W3E clreq 对中文行末字距、标点挤压的要求冲突。
- 汉字标签加字距后，字距宽度不随字号缩放（`em` 相对字号，`px` 绝对），大小标签的字距感不一致。

**落地**：本项目原 `.kicker`、`.sec-label`、`.path-hd`、`.tb-k`、`.tbl th`、`.specmenu-hd`、`.wire-hd` 等 9 处标签带 `letter-spacing: 0.04em–0.14em`，全部移除。强调改用**字重 + 颜色**（这两个在中文里都有效）。

### 4.2 `text-transform: uppercase` 禁用于中文标签

**规则**：打汉字的标签不得用 `text-transform: uppercase`。

**为什么**：对汉字完全无效——它不是「无效但无害」，而是**有害**：它让读代码的人以为这行在起什么作用，实际什么都没发生。真正的伤害是让规则失效而无人察觉。

例外：整段确实是西文（技能英文名、缩写）时可以保留，但那种场景应单独建类，不要和中文标签共用规则。

**落地**：本项目 9 处 `uppercase` 全部移除（内容确认：全是汉字标签——"专精"、"当前选中"、"这一波长什么样"、"技能"、"条件（什么时候用它）"）。

### 4.3 负 letter-spacing 保留

`h1`（-0.6px）、`h2`（-0.2px）、`.brand`（-0.2px）保留。收紧标题字距在中文里同样有效（减少字与字的松散感），且负值不会撑开字距。

## §5 无障碍硬底线

这三条不随审美变化，永远不豁免。

| 规则 | 来源 | 落地 |
| --- | --- | --- |
| 可聚焦元素必须有 `:focus-visible` 样式，焦点环对比度 ≥ 3:1 | WCAG 2.4.7 / Hallmark gate 26a | 全局 `:where(a, button, input, …):focus-visible` 规则，金色 2px 环 + 2px 偏移 |
| 有动效就要有 `prefers-reduced-motion` 兜底 | WCAG 2.3.3 / Hallmark gate 27 | `prefers-reduced-motion: reduce` 块，把动画时长压到 0.01ms、循环次数压到 1 |
| 颜色不单独承载信息 | Hallmark gate 41 / WCAG 1.4.1 | 本站语义色始终与文字或形状同时出现（如 `--up` 总配文字说明），不靠颜色单独表意 |

## §6 门禁

```bash
npm run check:design
```

跑在源码上，不需要浏览器。六组断言：

| 组 | 判据 | 级别 |
| --- | --- | --- |
| 间距阶完整性 | 相邻档差 ≥ 25% | 错误 |
| 间距取值 | 裸 px 必须落在阶内 | 错误 |
| 颜色字面量 | token 块外不得出现 hex | 错误 |
| 对比度 | 21 组配对 ≥ 4.5:1 | 错误 |
| 中文字距 | 中文标签不得用正 letter-spacing / uppercase | 错误 |
| 无障碍 | `:focus-visible` 存在；有动效须有 reduced-motion | 错误 |

### 6.1 与其他门禁的分工

| 门禁 | 管什么 |
| --- | --- |
| `check:design` | 间距、颜色、对比度、中文字距、无障碍 |
| `check:ui` | 真实 DOM：字号档位、内容宽、五段结构、图契约 |
| `check:copy` | 文案：禁用词、术语、AI 腔、长度预算、依据可追 |
| `check:doc` | 交付文档与落盘 JSON 逐字一致 |
| `validate:content` | 数据：数字有来源、runId 存在 |

## §7 走查顺序

Refactoring UI 的走查顺序是**因果链**，不是清单：

```
层级 → 间距 → 排版 → 色彩 → 深度 → 图像 → 收尾
```

理由：层级没理顺，什么算间距问题就会跟着变；间距一改，"这里到底要不要加条边框"这个问题往往自己就没了。

**本项目的走查清单**（每次改样式后按序过）：

1. **层级**：这一屏最重要的一件事是什么？它比第二重要的事明显吗？
2. **间距**：组内间距 < 组间间距吗？（Refactoring UI 法 5：组周围的空间必须大于组内部）
3. **排版**：字号只用四档（12/14/21/30）；正文行长 30–45 全角字；没有孤字成行
4. **色彩**：颜色全部来自 token？语义色是否与文字同时出现？
5. **中文字距**：新加的标签有没有误带 letter-spacing / uppercase？
6. **深度**：阴影表达的是层级，不是重要性
7. **收尾**：空状态存在吗？键盘能走完全程吗？

## §8 门禁自身的陷阱

**门禁会假通过。** 本轮就踩过一次，值得单独记下来。

`checkCjkTracking` 最初写成 `line.match(/letter-spacing\s*:\s*([\d.]+)px/)`——只认 `px` 单位。项目里正字距全用 `em`（`0.04em` / `0.1em`），所以**一条都没报**，门禁显示 0 错误，实际残留 4 处。

后来换实现时又踩了第二个坑：逐行扫描 + `inBlock` 标志位，单行规则（`.x { … }`）在同一行既开又关，声明体被整体跳过。

**现在的做法**：按 `{…}` 切块，块内做正则，单位同时认 `px` / `em` / `rem`。

**通用教训**：

1. 门禁报 0 不等于合规——**必须注入反向用例证明它真的会报**。本轮做法：手工改一处加回 `letter-spacing: 0.1em`，确认门禁立刻红，再还原。
2. 匹配器要按**单位与形态**穷举，不要只覆盖常见写法。
3. 单行规则与多行规则要同时处理，逐行扫描是最容易漏的形式。
