# 暗牧内容系统：搭建、复核与扩展手册

版本：1.0
冻结日期：2026-10-31

这份手册固定的是内容生产方法，而不是某一个版本的全部战术答案。当前已实装
Archon 暗牧的大秘境 DPS 内容；数据结构保留向治疗、团本和其他专精扩展的接口。

## 1. 产品目标

读者打开一页，需要依次得到四个答案：

1. 当前是什么场景：几只怪、持续多久、是否是首领、有没有加怪或阶段转换。
2. 这一场景应该做什么：爆发、保留、补 DoT、转目标或交防守。
3. 为什么这样做：来自模拟、日志、APL 或路线的哪一条证据。
4. 这条结论有多可靠：是单一高手样本、实测模拟、跨来源一致，还是仍待复核。

页面不是个人装备计算器，也不读取角色面板。属性、配装和木桩结论都基于固定的
测试 profile、固定预算和明确版本；换版本或换测试模板时整批重跑，不用旧角色快照
冒充当前状态。

## 2. 七条核心原则

### 2.1 决策先于数值

先回答“这一波开不开、为什么”，再展示 DPS、占比、评级和置信区间。数值服务于
判断，不把页面做成没有行动结论的数据仓库。

### 2.2 同一约束内才比较

只有游戏版本、英雄天赋、场景、目标数、时长、迭代数、profile 和模拟器版本相同的
两条记录，才能组成 A/B。跨目标数的绝对 DPS 不横向比较，只比较各自场景内的差值。

### 2.3 事实、推断、建议分开

每条内容至少保留三层：

| 层 | 回答 | 例子 |
| --- | --- | --- |
| 事实 | 日志或模拟直接显示了什么 | 第 9 段 285 秒，出现 2 次虚空形态 |
| 推断 | 这些现象说明什么 | 长波次需要把爆发拆到前后半段 |
| 行动 | 下一把具体怎么做 | 进本前确认两层充能，不在开场一次耗尽 |

推断不能伪装成事实；“没开爆发”不能直接推出“冷却漏用”，还要检查死亡、
转阶段、目标不可攻击和实时冷却状态。

### 2.4 模拟解释机制，日志校准现实

模拟擅长比较同一约束下的选择，真实日志擅长暴露移动、死亡、目标切换和路线节奏。
两者互相校验，不互相替代。

### 2.5 不确定性必须可见

页面上保留迭代数、置信区间、预测误差、样本状态和限制。没有数据就显示缺什么，
不用其他副本、其他专精或其他英雄天赋补洞。

### 2.6 内容与渲染分离

内容真源放在 `content/*.json`，组件只负责读取和表达。新增副本、场景或职业时，
优先扩展现有数据契约，不在 React 组件里复制一套业务结论。

### 2.7 人工裁决高于自动生成

自动流程可以生成草稿、候选结论和门禁结果，但不能自动把单样本提升为最终战术。
`sample-reviewed` 升为 `final` 前必须人工复核证据、语境和行动建议。

## 3. 数据分层

| 层 | 真源 | 责任 | 禁止事项 |
| --- | --- | --- | --- |
| 版本上下文 | `content/specs.json`、`content/profiles/*.simc` | 职业、专精、英雄天赋、APL、测试 profile | 不混用其他天赋或旧版 APL |
| 原始模拟 | `content/sims/*.json` | 每个 runId 的场景、DPS、CI、n、SimC 版本 | 不手改单条结果 |
| 原始日志 | `.tools/tmp/*events.json`、归一化后的 `content/logs/*.json` | WCL 筛选事件、Pull 边界、DoT 与爆发窗口 | 不拿截断摘要冒充完整事件 |
| 分析层 | `content/analysis/*.json` | 杠杆、伤害构成、A/B、动作预算、属性模型 | 不隐藏派生公式 |
| 策略层 | `content/strategy/archon-dungeons.json` | 总结、修正、优化与来源日志 | 不把假设写成确定失误 |
| 路线层 | `content/routes/*.json` | 波次、怪物、路线连线、地图投影 | 不伪造缺少的坐标 |
| 页面层 | `content/chapters/*.json`、`content/figures/chapters.json` | 五段结构、图契约、证据指向 | 页面组件不另写数字 |
| 表现层 | `apps/web/src/components/**` | 阅读顺序、交互和图形 | 不直接维护业务结论表 |

## 4. 标准生产流程

### 4.1 固定版本上下文

记录游戏版本、SimC 版本与 commit、profile 文件与哈希、英雄天赋、测试预算、
WCL 报告日期和路线 mapping 版本。

验收：任一页面数字都能回答“来自哪个版本、哪个 profile、哪一种场景”。

### 4.2 更新 profile 与 APL

将当前英雄天赋的 SimC profile 放入 `content/profiles/`，运行 APL 解析，生成：

- 技能中文名与条件表
- 38 行左右的原始 APL 优先级
- 人话条件
- 本测试模板用不上的种族、天赋和队友分支

“用不上”按固定测试模板解释，不写成“本角色没有”这类会随人物变化的表述。

### 4.3 建立场景矩阵

DPS 的当前最小矩阵：

| 场景 | 用途 |
| --- | --- |
| 单体 300 秒 | 长首领的稳定循环与冷却节奏 |
| 3 目标 300 秒 | 少量持续多目标 |
| 8 目标 300 秒 | 大波次高压多目标 |
| 5 小怪 30 秒 | 大秘境短波与加怪窗口 |
| 30 / 90 秒开不开爆发 A/B | 爆发窗口的直接收益 |
| 加怪窗口 | 目标数增长对决策的影响 |

场景必须由同一 profile、同一版本和同一迭代设置生成。场景名写清目标数、时长和
特殊条件，不能只写“AoE”。

### 4.4 跑原始模拟与派生分析

原始模拟完成后，再生成分析层：

- 禁用某个技能会掉多少
- 每个技能的伤害占比与真实影响
- DoT、增益、爆发与起手之间的依赖
- 动作预算与 GCD 去向
- 不同输出模型的属性曲线和最优配比
- 装备效果的相对贡献

每个派生结论必须引用 runId 或明确公式。预测值必须与一次真实复跑校核。

### 4.5 提取真实 WCL 数据

每个副本保留完整 Events 页筛选事件，记录：

- 报告代码、fightId、玩家、actorId、Key 和时长
- 目标专精、英雄天赋与来源 URL
- 完整筛选表达式
- WCL Fights 的真实 Pull 边界

事件归一化后生成：

- Pull 级施法序列
- 虚空形态窗口
- 核心 DoT 区间
- 施法频率、GCD 中位和活跃时间
- 与路线波次的怪物族重合度

死亡事件必须单独检查。死亡后的静默、缺窗口和低施法不能直接当作手法问题。

详细步骤见 `docs/WCL-ARCHON-PIPELINE.md`。

### 4.6 复核单样本打法

每条候选结论按以下顺序检查：

1. 数字是否与事件文件一致。
2. Pull 编号、绝对时间和相对时间是否对齐。
3. 是否存在死亡、转阶段、不可攻击或路线跳怪。
4. 是否能观察到冷却剩余、资源、充能和增益状态。
5. 行动建议是否只适用于这个样本，还是能解释触发条件。
6. 是否需要第二个样本才能下结论。

状态规则：

| 状态 | 含义 |
| --- | --- |
| `pending` | 没有可用样本 |
| `phase-only` | 只有阶段级数据 |
| `sample-reviewed` | 单样本 Pull 级数据已提取，候选结论待人工定稿 |
| `final` | 数据、事实、行动和限制均已人工复核 |

### 4.7 采集路线与地图

从 keystone.guru 同版本路线页提取：

- Pull 顺序与每波怪物
- 敌人世界坐标
- `killZonePaths` 路线连线
- 底图瓦片和楼层范围

页面按固定投影把世界坐标转换为地图像素。没有敌人坐标的空波次只保留在文字列表，
不在地图伪造落点。红玉这类只覆盖主层的地图必须保留范围提示。

详细步骤见 `docs/research/route-data-pipeline.md`。

### 4.8 成稿

每章保持五段：

| 段 | 回答 |
| --- | --- |
| ① | 当前场景和目标数量是什么 |
| ② | 这一场景的核心决策是什么 |
| ③ | 技能顺序如何随场景调整 |
| ④ | 这条决策落在真实路线哪里 |
| ⑤ | 真实高手或模拟执行怎么打，限制是什么 |

页面先给行动，再给依据。表格、曲线和日志明细放在支撑位置；技术标识、runId 和
原始记录进入折叠区或页底证据条。

### 4.9 门禁与发布

内容完成至少运行：

```text
npm test
npm run typecheck
npm run validate:content
npm run check:doc
npm run check:copy
npm run check:design
npm run check:ui
npm run check:static
npm run audit:text -- --strict
npm run verify:gates
```

只有内容、图和交互都属于同一数据源，门禁才算有效。一个段位写着“有图”，但 DOM
没有真实图或路线，必须判定失败。

## 5. 页面表达规范

### 5.1 字体层级

- 正文：Noto Sans SC 优先，随后使用系统中文字体。
- 页面主标题与段标题：Noto Serif SC 优先，建立克制的编辑层级。
- 数字、runId、时间、评级：等宽字体与等宽数字。
- 中文标题不使用正值字距，避免行末松散。

### 5.2 四属性视觉编码

暴击、急速、精通、全能必须同时使用：

- 四种明确不同的色相
- 实线、虚线、点线、点划线
- 文字标签与数值

颜色不是唯一信号。图例、曲线、配比条和热矩阵中的同一属性必须保持同一颜色语义。

### 5.3 数值表达

- “高多少”必须注明比较对象。
- “多少 DPS”必须注明场景和时长。
- 百分比增益与绝对伤害增量分开写。
- CI、预测误差和样本数放在结论附近。
- 固定测试预算不写成玩家当前属性。

## 6. 扩展到治疗

### 6.1 不直接复用 DPS 结论

治疗的核心不是“谁伤害高”，而是“在可存活约束下，用多少资源和施法覆盖伤害事件”。
DPS 排名、敌方目标数和爆发增量不能自动转换为治疗优先级。

### 6.2 治疗场景矩阵

建议至少覆盖：

| 维度 | 场景 |
| --- | --- |
| 持续伤害 | 5 人持续掉血、团本稳定掉血 |
| 尖刺窗口 | 可预判的大伤害、不可预判的点名 |
| 坦克压力 | 平砍、重击、持续 DoT |
| 分散 / 集中 | 集合治疗与分散救急 |
| 移动 | 可站定、短移动、长移动 |
| 资源 | 高蓝耗、低回蓝、连续施法 |
| 冷却覆盖 | 单个大招、多轮小技能、外部减伤 |

### 6.3 治疗指标

除 HPS 外还要保留：

- 有效治疗与过量治疗
- 伤害事件覆盖率
- 关键窗口存活结果
- 目标选择与队友覆盖
- 法力、资源、充能和冷却
- 外部减伤与队友重叠
- 移动损失与施法中断
- 单次决策的机会成本

页面结论应写成“这个窗口用什么工具保证什么结果”，不是只看 HPS 排名。

### 6.4 治疗数据结构

现有场景契约需要增加：

- `role: healer`
- 友方目标与伤害事件
- 可预判 / 不可预判标签
- 目标血量与减伤状态
- 资源开始值、消耗和恢复
- 成功条件，例如无人死亡、最低血量、过量治疗上限

## 7. 从 M+ 扩展到团本

### 7.1 保留的共同核心

以下能力不随模式变化：

- 固定版本和 profile
- 同约束 A/B
- runId 证据
- 事实 / 推断 / 行动分层
- 不确定性展示
- 自动生成与人工复核
- 五段阅读结构

### 7.2 替换的场景对象

大秘境以“路线波次”观察战斗，团本以“首领阶段和伤害事件”观察战斗。团本适配层
需要把 `wave/pull` 替换或补强为：

- encounter
- phase
- damage event
- assignment
- movement window
- immunity / defensive window
- add spawn

地图可以保留为背景，但团本的主要时间轴应是阶段、机制和伤害窗口，不是地牢路线。

### 7.3 可扩展契约

建议统一以下语义：

| 字段 | 取值 |
| --- | --- |
| `contentMode` | `mplus` / `raid` |
| `role` | `dps` / `healer` |
| `windowKind` | `pull` / `phase` / `damage-event` / `adds-window` |
| `unitRelation` | `enemy` / `ally` / `self` |
| `objective` | `damage` / `survival` / `throughput` / `resource` |

各角色和模式使用同一证据框架，但指标、场景和成功条件分别定义。

## 8. 结论卡模板

每条可发布结论建议保持以下结构：

```json
{
  "title": "一句可执行判断",
  "fact": "时间、波次、目标数、窗口或模拟差值",
  "inference": "这组事实支持什么判断",
  "action": "下一把具体怎么做",
  "limit": "死亡、转阶段、单样本或缺少实时冷却等限制",
  "sources": ["runIds / WCL Pull / 路线"],
  "status": "sample-reviewed"
}
```

如果 `fact` 还不能支持 `inference`，结论保持候选状态，不进入最终页面的肯定句。

## 9. 维护规则

| 变化 | 必须重跑 | 页面处理 |
| --- | --- | --- |
| 游戏小版本、套装或职业改动 | profile、模拟、分析、章节数字 | 旧版结论标失效，不静默沿用 |
| APL 改动 | 优先级表、依赖、杠杆、动作预算 | 检查章节是否引用旧顺序 |
| 新增 WCL 样本 | 事件归一化与策略复核 | 单样本结论只能升级，不覆盖证据 |
| 路线或地图 mapping 改动 | 路线 JSON、地图投影、路线门禁 | 旧地图不得继续显示新坐标 |
| 玩家本人换装备 | 不需要更新页面 | 页面使用固定测试模板，不追踪个人面板 |
| 要生成个人建议 | 另建临时任务或外部工具 | 不写入长期内容真源 |

## 10. 完成标准

一套内容达到可交付状态，需要同时满足：

1. 主要场景都有明确行动结论。
2. 每个数字能追到 runId、日志或路线来源。
3. 所有比较都在同一约束内。
4. 页面不依赖玩家当前装备或人物属性。
5. 单样本结论保留限制和复核状态。
6. 路线、波次、地图与文字指向同一份数据。
7. 四属性不只靠相近颜色区分。
8. 正文字体、标题层级和数字排版一致。
9. 自动门禁通过，且坏样本能被门禁拦住。
10. 最终战术由人工确认，不由生成器自动定稿。
