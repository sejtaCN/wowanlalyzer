# 界面美观优化方案（文字内容 + 可读性）

> 目标：把网站从「能用的数据站」推到「读得下去的教学站」。
> 范围：只动**文案与排版层**，不碰底层内核与业务逻辑。
> 诊断日期：2026-10-27。诊断方式：读代码 + `npm run build` + Puppeteer 逐屏截图（`.tools/tmp/audit/`）。
> 配套文档：`docs/guide-content-rules.md`（**文案规范源**，本方案的 §2 §3 已上移过去）、
> `docs/writing-style.md`（页面级精简版）、`docs/ui-design.md`（长什么样）、`docs/HANDOVER.md` §5（待办）。

## §0 一句话结论与范围判定

**中部区域 = 章节页（11 章主体阅读页）**，它在信息架构里正好卡在首页与解析台之间，是用户停留时间最长的页面，也是文案与排版问题最集中的地方。本方案以章节页为主战场，首页与解析台的**中部区块**同步纳入。

实测三类问题的主要落点（数字均为代码统计，非估计）：

| 问题 | 落点 | 实测量 |
| --- | --- | --- |
| ① 开发过程中的中间文字 | TSX 硬编码文案 + 首页/解析台状态条 | 12+ 处（含 `按 B3 顺序补`、`content/sims`、`sims-run.mjs`） |
| ② 未本地化英文 | 章节 `evidence` 字段 + 技能键 + 证据条 | **33 条 evidence 中 28 条含裸代码/英文键**；**25 个技能中 14 个并列显示英文键**；证据条直接暴露 `dec_voidform_on_0__w30_8__5000` |
| ③ AI 生成痕迹 | 不是套话，是**结构同构**：每段 note 都是「结论 + 补充 + 免责」三段式 | 5 段模板固定，note 全部以分号并列收尾 |
| ④ 附带发现 | 章节页第⑤段把 4 段灰色小字堆在一起；`ChapterSections.tsx:428` 的 `**` 标记**原样显示在页面上** | 1 处渲染 bug（见 §3.6） |

**不动区（红线）**：`content/sims/**` 原始数据、`content/profiles/**`、SimC/APL 解析链、`packages/learning-core` 的进度与内容模型、图契约 `content/figures/chapters.json` 的状态判定、`scripts/**` 的跑批逻辑。所有结论与数值来源一个都不动——本次只改**它们怎么被说出来**。

## §2 文案改写原则

> 本节是**改写对照的原始出处**（12 条前后对照 + 六条原则）。可复用的规范版在
> `docs/guide-content-rules.md` §4（通用语言规范）与 §5（AI 味十二条）。

### 2.1 六条原则

**P1 · 一句话只做一件事。**
现在每段 note 是「结论 + 补充 + 免责」三段式（例：`开与不开的差：+44.0%，一次爆发多 12.7M；误差带 ±0.26%。` → 段⑤更是 4 段并列）。改写后每段 note 只保留**读者动作**，最多两句。

**P2 · 写「怎么做」，不写「怎么做的」。**
禁止描述实现过程。「表格来自 APL 原文，条件只做词替换，不改写逻辑」→ 读者不需要知道替换逻辑。

**P3 · 数据先行，判断收尾。**
一个数字都不许裸奔：必须带单位（只 / 秒 / M / %）、带口径（模拟 or 真实日志）。这一点项目已经做得很好，继续保持。

**P4 · 限制归限制，不冒充结论。**
数据边界是必要的，但必须**降级到折叠区**，并且用读者语言重写，而不是用管线语言。

**P5 · 禁自指与自夸。**
不写「不用改界面」「页面自动长出来」「这是真实组件的骨架」——读者不关心代码怎么搭。禁「唯一」「一定」「必须」「完全」（除非有数值支撑）。

**P6 · 语气对齐站内已有的好文案。**
以 `casePanel.reading` 为标尺。例（现状，写得好）：
> 三段都是持续 3 分钟以上的多目标区。大波值钱，但真正的条件是"这一段够长、能吃到第二次冷却"。

同样的语气要求适用于所有 note。

## §3 中英文内容处理规范

> 术语三分类的规范版在 `docs/guide-content-rules.md` §4.2；本节保留完整清单与逐条处理记录。

### 3.1 三级术语分类

| 级别 | 定义 | 处理方式 | 本项目实例 |
| --- | --- | --- | --- |
| **L1 · 保留英文** | 中文玩家圈通用缩写，离开中文语境也没歧义 | 正文直接用，首现处加 `Gloss` 悬停 | DPS、APL、GCD、CI、DoT、buff、N+1 |
| **L2 · 中文化** | 有确定中文译名，且读者能理解 | 页面写中文，英文进悬停 | runId→模拟记录号、SimC→模拟器、Jaccard→重合度、commit→版本号、Action Priority List→技能优先级表 |
| **L3 · 绝不出现在正文** | 内部实现产物，读者零收益 | **移出页面**（折叠区 / 数据面板） | APL 表达式原文、英文技能键、场景 id、文件路径、批次号、脚本名、门禁术语 |

### 3.2 L3 清单（本次必须处理）

**a) APL 表达式原文 —— 28 条**

现状（`content/chapters/*.json` 的 `priorityDiff.evidence`）：

```
APL: active_dot.shadow_word_pain>=active_dot.vampiric_touch
APL: actions.main+=/void_volley 排在前段；模拟 w30_8 增益稳定
APL: (priest.force_devour_matter|target.has_absorb)&talent.devour_matter
APL: actions+=/call_action_list,name=aoe,if=active_enemies>2
APL: tentacle_slam,if=raid_event.adds.in>30 | raid_event.adds.in>5&full_recharge_time<=gcd.max*2
```

改法（两个动作）：
1. **正文写中文条件**，例：`APL: active_dot.shadow_word_pain>=active_dot.vampiric_touch` → `痛 的持续伤害层数已经追平 触须猛击，就不用再补`；
2. **原始 APL 行移入 `<details>`「查看优先级表原文」**，满足"结论必须可见地挂着证据"（`ui-design.md` §1.3），又不在正文裸奔。

> 注意红线 1：改写**不删除**证据，只是把它从正文挪到可展开处，并保证仍能追到 APL 与 runId。

**b) 英文技能键 —— 14 / 25 个技能**

`skills.json` 里 11 个 `verified: true` 只显示中文，14 个 `verified: false` 会**并列显示英文键**（`ChapterSections.tsx:177,206`）。实测页面上出现 `shadow_word_madness`、`tentacle_slam`、`mind_flay`、`arcane_torrent` 等。

改法：英文键移入 `Gloss` 悬停（`glossary.json` 已有 `en` 字段，无需新建数据），页面只留中文名 + 一个统一的"待核对"标记，而不是每个技能下面挂一行 12px 灰字。

**c) 场景 id / runId / 文件路径**

| 现状 | 改后 |
| --- | --- |
| `模拟 w30_8 增益稳定` | `8 只目标 · 30 秒` |
| `模拟 w30_2 与 w45_1 的增量低于大波档` | `2 只和 1 只的增量都低于大波` |
| `观测冷却 122.4s（archon__st / t3 动作序列）` | `观测冷却 122.4 秒（执政官 · 单体目标）` |
| `每一行都对应 content/sims 下的一个同名文件` | `点开任意一行，看它的模拟版本、迭代次数和误差范围。` |
| `sims-run.mjs` / `leverage.mjs` / `validate:content` | 只在「未实装专精」页的"怎么补数据"表里出现（那一页本身就是给开发者看的，**保留**） |

**d) 批次号与工程词**

`按 B3 顺序补` → `计划顺序`；`门禁` / `跑批` / `批次` / `门禁自检` 一律不出现在读者页面。

### 3.4 数字与单位规范

- **单位不省略**：`12.7M` → `12.7 百万`？→ **否**。社区语境保留 `M`，但补全为 `12.7M 伤害`。

## §4 排版设定

### 4.1 现状问题（实测）

| 项 | 现状 | 问题 |
| --- | --- | --- |
| 字号档位 | `30 / 21 / 14 / 12`（`--fs-1..4`） | 21→14 跨了 7px，**h3（17px 语义）无处安放**；14→12 只跨 2px，**12px 同时承担图注/表格单元/标签/证据条/图例 5 种角色** |
| 正文 measure | 内容宽 720px ÷ 14px = **51 全角字/行** | 中文舒适行长 30–45 字，**超宽 15–40%**；`.hero p` 用 `60ch` 限过、正文没限 |
| 行高 | body `1.65`；note `1.6` | 中文正文需要 1.7–1.8；12px 灰字块 1.6 更挤 |
| 间距 | 全站只有 `--gap: 14px` | **段间距 = 段内图间距 = 14px**，页面读起来是一根没有节奏的柱子 |
| 字体栈 | `Inter, system-ui, 'Microsoft YaHei'` | **`Inter` 从未被加载**（无 `@font-face`、无 Google Fonts link），实际落到 Segoe UI + 微软雅黑，中西文基线不齐 |
| 中文排版 | 无 | 缺 `text-wrap: pretty`、`word-break` 保护，中英混排易出现孤字与断词 |

### 4.2 目标设定

#### 字号：4 档 → 6 档（语义化）

| Token | 值 | 用途 | 对应现状 |
| --- | --- | --- | --- |
| `--fs-display` | 30px | 页面主标题（每页一次） | `--fs-1` |
| `--fs-title` | 21px | 区块主标题 / h2 | `--fs-2` |
| `--fs-sub` | **17px** | 图表标题（h3）、卡片标题、段内小标题 | **新增** |
| `--fs-body` | 14px | 正文、结论句、列表 | `--fs-3` |
| `--fs-meta` | **13px** | 表格单元、次要信息、卡片元信息 | **新增** |
| `--fs-caption` | 12px | 图注、证据条、chip、图内刻度 | `--fs-4` |

**关键变化**：`12px` 从"什么都干"退化为**只做图注与图内刻度**；所有读者要读的说明文字升到 `13px`；图表标题升到 `17px`，与 `21px` 拉开层级。

> ⚠️ **同步项**：`scripts/check-ui.mjs` 的 `FS_OK = new Set(['30px','21px','14px','12px'])` 会拒绝任何新字号。改 CSS 的**同一批次**必须把白名单改成 6 档，否则 `npm run check:ui` 直接红。字号白名单应改为**从 CSS 变量派生**，而不是硬编码字符串。

> **2026-10-29 实测**：本项已按「从 CSS 变量派生」落地——`scripts/check-ui.mjs:48-53` 读 `ui.css` 的 `--fs-*` 生成 `FS_OK`，六档为 36/24/18/16/14/12；`apps/web/index.html` 与 `ui.css` 的 `color-scheme` 均为 `dark`。

| --- | --- | --- |
| `--fs-display` 30px | 1.25 | 37.5 |
| `--fs-title` 21px | 1.4 | 29.4 |
| `--fs-sub` 17px | 1.45 | 24.7 |
| `--fs-body` 14px | **1.75** | 24.5 |
| `--fs-meta` 13px | 1.7 | 22.1 |

#### 间距：1 档 → 5 档（形成节奏）

| Token | 值 | 用途 |
| --- | --- | --- |
| `--sp-1` | 4px | 图标↔文字、chip 内边距 |
| `--sp-2` | 8px | 组件内部（标签↔值、标题↔副标题） |

| `--sp-5` | **40px** | 页面大区块之间（hero→章节组→教练卡→状态条） |

#### 正文 measure 收窄

- 页面容器保持 `--content: 720px`（表格与图件需要这个宽度）。
- **新增 `--measure: 36em`（约 504px @14px）**，作用于：`.claim`、`.sec-note`、`.hero p`、`.page-sub`、`.casebox p`、教练卡正文。
- 效果：正文行长从 51 全角字降到 36 字；**表格与图件仍是 720px**，形成"窄正文 / 宽图件"的标准文档版式（Linear Docs、Stripe Docs 同款做法）。
- `ch` 单位在中文里按 `0` 宽计算，必须用 `em` 而不是 `ch`。

#### 字体栈

```
正文： system-ui, -apple-system, 'Segoe UI', 'PingFang SC', 'Microsoft YaHei', 'Noto Sans SC', sans-serif
数字： ui-monospace, 'Cascadia Mono', 'SF Mono', Consolas, monospace
```
- 删掉未加载的 `Inter`（避免"看起来加载了其实没有"的误导）。
- 数字统一 `font-variant-numeric: tabular-nums`（现状 `.mono` 已有，扩展到所有数值 span）。
- 补 `text-wrap: pretty`（标题与结论句，避免孤字）与 `overflow-wrap: anywhere`（中英混排的长键名不撑破布局）。
- 保持 `lang="zh-CN"`（已正确）。

### 4.3 颜色与对比度（可读性）

现状色板：`--ink #f8fafc` / `--sub #b8c2d0` / `--muted #94a0af` on `--bg #0b0e13`。

- `--muted #94a0af` on `#0b0e13` 对比度 ≈ **7.2:1**（AA 通过），可保留。
- 但**当前大量说明文字用 `--muted` 12px**——即使对比度合格，字号 + 次要色叠加，可读性明显下降。改写后：说明句升 `13px` 且用 `--sub`（≈10.5:1），只让图注/刻度保留 `--muted`。
- 表格单元从 `12px` 升 `13px`，长表格的扫读压力下降。
- **不建议**改动主题色与底色——`ui-design.md` §6 已采样 WowCoach 定稿，色板不是本次问题所在。

## §5 信息层级与视觉节奏（中部页面各区块布局建议）

现状结构（`ui-design.md` §4.1）：`面包屑 → 顶图带 → ① ② ③ ④ ⑤ → 证据条`。结构本身没问题，**问题是段与段之间没有层级差**。

### 5.1 总体节奏

```
面包屑（12px 弱）
  ↓ 24px
顶图带（结论区：最高视觉权重，金色/绿）
  ↓ 40px  ← 唯一的大分节
① 编号 + 一句话 → 图 → 一句说明        ← 段间 28px
  ↓ 28px
② ...
  ↓ 28px
⑤ ...
  ↓ 40px  ← 与证据条之间加大分隔
证据条（12px 弱，视觉最轻）
```

**关键改动**：段间距 `14px → 28px`，顶图带下/证据条上 `→ 40px`。这一处改动对"可读性"的贡献最大——不需要动任何内容，页面立刻从"一根柱"变成"五节"。

### 5.2 逐区块调整

| 区块 | 现状问题 | 建议 |
| --- | --- | --- |
| **顶图带 TopBand** | 三格等宽，但左格是图、中格是大数字、右格是结论，**权重倒挂** | 三格权重改为 `1.2fr / 0.9fr / 1fr`；右格"该做什么"用金色实底 chip（唯一的金色实底区），成为页面的行动锚点 |
| **① 模型卡 / 目标数轴** | `model-grid` 四个数字 + `claim` + `note` 三层堆叠，无视觉分组 | 四个数字做 2×2（窄屏 1×4），`claim` 单独加金色左边框成"结论条"，`note` 降为 caption |
| **② 主图** | 图内已有说明，图下又一句 note，**重复** | 图下 note 只保留"这张图怎么读"（如"两行各自是真实 DPS，不是把增量叠在原条上"），**删掉复述数字的那句** |
| **③ 技能调整 PriorityMap** | 图例 4 条全是自述（"序号 = 38 条 APL 表…""位置点与卡片 # 号一一对应"）→ 2 条英文 raw code | 图例压到 1 条；`evidence` 改中文条件句；原始 APL 行进 `<details>` |
| **④ 地图** | 左侧 720px 大图 + 右侧窄栏，图注说"只给地形"——但占了两格 | 图与注记上下堆叠（图宽 100%），注记折叠进 `<details>`；L2 保留左右分栏（图+当前波） |
| **⑤ 高手对照** | **最严重**：4 段灰色小字堆叠（推断方法 / 读法 / 限制 / 段说明），全部同权重 | 保留 1 段"读法"（读者必需）；其余 3 段折进 `<details>`「这段是怎么算出来的」；`casebox` 的 headline 用 17px 提为段内小标题 |
| **证据条 EvidenceBar** | 直接外露 `dec_voidform_on_0__w30_8__5000`、`trace_archon` | 默认：`8 只目标 · 开/不开对照 · 各 5000 次 · 模拟器 1210.01 · 2026-10-25`；原始记录号进折叠；`组` 那一行删除 |
| **首页中部** | 状态条与章节组之间无分隔；`还没写` 那格是灰字占位 | 状态条移到底部并做弱化；空态改成"这一组还没写" + 计划顺序（删批次号） |
| **解析台中部** | 六段全是同宽表格，**整页约 8 屏高**，无小标题分层 | 每段加 17px 小标题；⑥ 的 246 行表格默认只显示每组前 12 行 + "展开全部"，其余收进 `<details>` |

### 5.3 段落内部的说明句规范（本次最核心的排版动作）

**现状**：每段 note 都以 `.sec-note`（12px `--muted`）呈现，多段并列时形成灰字墙。

**改后**：

```
① 这一波几只、活多久                      ← h2 21px（段标题，问题式）
┌─────────────────────────────────────┐
│  图 / 表                              │  ← 720px
└─────────────────────────────────────┘
这是一波 8 只怪、打 30 秒的模型。移动和
危险点还没折算进伤害，数字偏保守。        ← 13px --sub，最大 36em，两句以内
```

- 说明句**最多两句**，超过就进折叠或拆到下一段。
- **禁止**出现三段式并列。
- 关键：说明句是**给读者的判断**，不是给系统的免责声明。

## §10 附：本方案的取舍说明

- **为什么不动 `claim` 和 `casePanel`？** 这两处实测是全站质量最高的文案：直接、数据先行、有人话、有边界感（例：`三段都是持续 3 分钟以上的多目标区。大波值钱，但真正的条件是"这一段够长、能吃到第二次冷却"。`）。它们是本次改写的**参考范本**，不是问题所在。动它们是纯粹的风险收益倒挂。
- **为什么证据不删只折叠？** `ui-design.md` §1.3 要求"结论必须可见地挂着证据"。裸 APL 表达式的问题是**位置太靠前**，不是**存在**。折叠区既守住证据链，又让正文干净。
- **为什么字号从 4 档扩到 6 档而不是压成 3 档？** 现状 12px 一个人干五种活才是可读性下降的主因；压档会让问题更糟。扩到 6 档需要同步改 `check-ui.mjs` 的白名单——这是本方案里唯一一处**必须动门禁**的改动，必须同批次提交，否则 CI 会红。
